# Internal app deployment process

The two app workflows are manual-only and deploy the immutable `main` commit that triggered the run. They require `APP_VERSION` (one to three numeric components) and a positive `APP_BUILD_NUMBER`; each platform refuses to continue unless the exact commit already has a successful `CI` push run.

## Repository setup deferred to #117

Developer accounts do not exist yet, so this repository only implements and credential-free tests the process. Before the first run, create the `android-internal` and `ios-testflight` GitHub environments, restrict them to `main`, configure an approval rule, and set `ANDROID_INTERNAL_DEPLOY_ENABLED=true` or `IOS_TESTFLIGHT_DEPLOY_ENABLED=true` only after reviewing the frozen source/version.

Android needs an enrolled Play developer account, an existing app record for `kr.co.cotton.vlrgg_mobile`, a compatible upload key, internal testers, and these environment secrets: `API_BASE_URL`, `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`, and `ANDROID_PLAY_SERVICE_ACCOUNT_JSON`. The service account must be limited to the existing app and internal release work; the workflow materializes the keystore only in runner temporary storage and removes it and the signed bundle on success or failure.

iOS needs Apple Developer Program and App Store Connect enrollment, an existing app record for `kr.co.cotton.vlrggmobile`, a compatible distribution certificate/profile, internal testers, and these environment secrets: `API_BASE_URL`, `IOS_TEAM_ID`, `IOS_CERTIFICATE_BASE64`, `IOS_CERTIFICATE_PASSWORD`, `IOS_PROVISION_PROFILE_BASE64`, `APP_STORE_CONNECT_KEY_ID`, `APP_STORE_CONNECT_ISSUER_ID`, and `APP_STORE_CONNECT_KEY_CONTENT_BASE64`. The lane derives the profile UUID, refuses to overwrite an existing installed profile, and creates only a temporary keychain/profile/configuration. Fastlane 2.239.0 uses an owned temporary API-key directory with pinned Xcode 26.6; cleanup never removes credentials from the user's home key directory.

Run only from the Actions page on `main`; the lanes reject any other invocation and require the checkout HEAD, workflow SHA, and frozen source SHA to match. A rerun preserves the original source SHA and input version. Workflow concurrency serializes only these repository workflows, not local or store-console uploads. Both lanes query the target store before upload and refuse reported reused build numbers, but those queries expose only limited published states: a missing result is not proof that an uncertain upload failed. If an upload response is lost or processing is incomplete, explicitly verify the Play Console bundle/track receipt or App Store Connect TestFlight build status before starting a fresh workflow; a lookup error fails closed. The APIs cannot prove signing compatibility or every in-flight receipt without enrolled accounts, so #117 must validate account roles, agreements, app records, current build numbers, signing identity compatibility, environment protection, upload receipt, tester availability, and physical-device installation.
