# Server FCM Match Notification — Stage 1 technical contract

- Status: Accepted implementation contract; implementation has not started
- Scope: `server` only, local/private and fully offline-verifiable
- Related: [ADR-0001](adr/0001-match-notification-stage1-storage-and-provider-boundary.md), [Matches product contract](../feature/matches/README.md), [server architecture](server-arch.md)

## Scope and boundary

Stage 1 adds a Match-notification vertical slice under the existing Matches feature: durable target subscription intent, target-scoped revision ordering, unique START/END intents, fixed-delay tracking, durable delivery state, a provider-neutral seam, and a Firebase Admin implementation. It is server-only. The current server remains the baseline until a later implementation changes it: it has direct Netty construction, manual composition, scraping APIs, and common safe errors, but no notification sources, database/migrations, Firebase Admin dependency, or scheduler.

Stage 1 excludes all `app/` code and tests, live credentials/project/network/dry-run, device-display proof, public deployment, production data, authentication or target ownership, and multi-instance scheduling. Feature and notification API enablement are independent and default to `false`. API-enabled Stage 1 is deliberately loopback-only; this can make it unreachable from another device, which is acceptable because App integration is excluded. A registration value is an anonymous push address, never an account, physical-device identity, authentication credential, authorization proof, or ownership proof.

## Public target and listener authority

Public request/response terminology is provider-neutral: `registrationValue`. The domain receives an opaque `PushTarget`; neither public APIs nor domain types expose FID, token, account, or device identity. `notifications.firebase.target-mode` is the only internal Firebase adapter selector: case-sensitive `FID` (default) or `LEGACY_TOKEN`. The selected mode is persisted with target/store metadata, and an unsupported mode or persisted mismatch stops startup before ADC, FirebaseApp, provider, routes, or jobs. Implementation-day primary-source revalidation is required for Admin SDK versions, message builders, error mapping, and both modes.

There is no approved public authority design in Stage 1. Mutation/state endpoints are local/private, separately disabled by default, and must never infer authority from a registration value. When APIs are enabled, the one actual Netty listener must use the same immutable `ServerListenerConfiguration` object consumed by notification preflight, and its host must be exactly literal `127.0.0.1` or `::1`. Hostnames, wildcards, non-loopback addresses, forwarded headers, self-asserted ingress labels, and additional connectors are rejected before route/resource work. Background jobs may run with APIs disabled on a non-loopback listener.

## Desired state, observations, and durable delivery

A logical subscription is one `(target, Match)` pair. Per target, a positive signed `Long` revision orders all mutations: a stale revision does nothing; the same revision with the same canonical operation replays idempotently; the same revision with another operation conflicts; and `Long.MAX_VALUE` has no later distinct mutation (`REVISION_EXHAUSTED`) and never wraps. Global OFF changes only that target's active subscriptions. Constraints are unique subscription `(targetId, matchId)` and unique intent `(targetId, matchId, eventType)`.

The tracker polls each active unique Match ID once per fixed 10-minute delay cycle. First successful observation is baseline only. `UPCOMING`/`POSTPONED -> LIVE` creates START; `LIVE -> COMPLETED` creates END; `UPCOMING`/`POSTPONED -> COMPLETED` creates END only. First LIVE/terminal, repeat, time change, cancelled, missing, network, and parsing observations create no intent. Network, parsing, upstream-missing, and public Match status remain distinct. FCM acceptance is provider acceptance, not device delivery.

The intent state machine is:

```text
PENDING | RETRY_WAIT --claim--> CLAIMED_NOT_STARTED --commit call marker--> CALL_STARTED
CALL_STARTED --provider accepted--> ACCEPTED
CALL_STARTED --typed retry--> RETRY_WAIT | TERMINAL_FAILURE
CALL_STARTED --proven invalid--> INVALID_TARGET (transactional cleanup)
CALL_STARTED --timeout/cancellation/ambiguous I/O/recovery--> UNKNOWN
CLAIMED_NOT_STARTED --lease expiry--> reclaimable
CALL_STARTED --lease expiry/recovery--> UNKNOWN
```

Claiming stores a lease and claim token. The service validates the message, then in a separate committed transaction verifies the token, increments `applicationAttemptCount` exactly once, and moves the row to `CALL_STARTED`; only then does it call the adapter outside a transaction. The timeout is monotonic, default 30 seconds, range 1–60 seconds; its claim lease defaults to 120 seconds, range 10–600 seconds, and is strictly greater than the timeout. Finalization is a CAS from the same state/token. Late adapter results after `UNKNOWN` are ignored and counted only with a safe category. `CLAIMED_NOT_STARTED` expiry never increments attempts; `CALL_STARTED` expiry, timeout, uncertain cancellation, and untyped I/O become `UNKNOWN`, which is never due, claimed, or automatically resent. This explicitly admits a possible loss between the call-marker commit and SDK entry.

## Retry and provider-minimum contract

Application attempts are committed adapter-invocation boundaries, not claim attempts or Firebase SDK internal HTTP retries. Defaults and limits are: maximum application attempts 5 (1–10), initial retry 30,000 ms (1,000–600,000), maximum application retry 3,600,000 ms (initial through 86,400,000), deterministic jitter maximum 5,000 ms (0–60,000 and not above application maximum), and provider-minimum safety ceiling 86,400,000 ms (60,000–604,800,000). The adapter has no immediate retry loop.

For a typed retry after one-based attempt `a`, exhaustion is evaluated first: if `a >= maxApplicationAttempts`, persist `TERMINAL_FAILURE/RETRY_EXHAUSTED` without parsing headers, generating jitter, or calculating a due time. Otherwise use a saturating `initialRetry * 2^(a-1)` capped at the application maximum, then add deterministic jitter capped at that same maximum. Jitter is zero when disabled; otherwise it is the unsigned big-endian first eight bytes of SHA-256 over NUL-separated UTF-8 values `vlrgg-retry-jitter-v1`, canonical intent UUID, `START`/`END`, and the unsigned decimal attempt, modulo `retryJitterMaxMillis + 1`.

`Retry-After` names are ASCII case-insensitive and only one scalar string value is accepted: trimmed ASCII delta seconds or a future IMF-fixdate calculated from one captured wall-clock instant. Absent, malformed, duplicate, untyped, negative, or past values use a fallback. A valid provider minimum is a true minimum, never reduced by the application cap. Final HTTP 429 uses a valid minimum or an irreducible 60,000 ms; final HTTP 503 uses a valid minimum or normal application backoff; another retryable typed response requires implementation-day official support. A valid provider minimum above the safety ceiling becomes `TERMINAL_FAILURE/PROVIDER_RETRY_AFTER_UNSAFE` with no automatic retry. Checked wall-clock addition overflow becomes `TERMINAL_FAILURE/RETRY_SCHEDULE_OVERFLOW`.

The successful retry CAS persists decision wall time, delay, and due time. Eligibility requires both the persisted wall due time and a feature-process monotonic guard. The originating process stores the guard with that exact schedule tuple; scans, scanner reconstruction, and same-JVM delivery-worker restart must reuse it. On a process reopen, atomic compute-if-absent creates one full-delay guard for a row/schedule; genuine in-process cache loss emits only `retry_guard_anchor_lost` and creates one new full guard. A stable process becomes eligible once both conditions pass. Every distinct process restart may add one full stored delay, so repeated restarts have no finite liveness bound; this is the accepted Stage 1 safety-over-liveness limitation.

## Persistence, invalidity, and H2 boundary

Stage 1 uses a file-backed H2 JDBC URL with absolute local path and `AUTO_SERVER=FALSE`, `DB_CLOSE_ON_EXIT=FALSE`, `LOCK_TIMEOUT=10000`, and `WRITE_DELAY=0`; it rejects in-memory/remote/automatic-server forms. Flyway migrations, bounded owned JDBC pool (default 4, range 1–8), and H2 claim SQL stay in the H2 adapter. `Dispatchers.IO.limitedParallelism` is not a database pool. H2 is disposable local single-JVM state: public/production exposure, multi-instance ownership, and more than one H2 owner fail before DB or ADC initialization. Separate JVM testing only proves committed-marker state readability for the selected local JVM/filesystem; it does not prove power-loss durability, corruption recovery, PostgreSQL isolation, or multi-process safety.

The enabled-only `VLRGG_NOTIFICATION_LOOKUP_DIGEST_KEY` is canonical 43-character unpadded base64url decoding to 32 bytes. Its lookup digest is full HMAC-SHA-256 over NUL-separated `vlrgg-match-notification-target-v1`, provider discriminator, target mode, and registration value. It is a keyed lookup/collision-resistance mechanism, not encryption. Store metadata retains non-secret SHA-256 key ID, challenge, verifier, and target mode; reopen compares ID and verifier in constant time. No Stage 1 key rotation, implicit adoption, or target reuse is allowed.

On provider-proven permanent invalidity, one transaction marks the target non-sendable, disables only its subscriptions, terminalizes unsent `PENDING`, `RETRY_WAIT`, and `CLAIMED_NOT_STARTED` intents, preserves `CALL_STARTED`/`UNKNOWN` ambiguity from resend, and logically erases the raw provider value. Every queryable active/tombstone, subscription, intent, audit, metadata, repository-projection, and serialized-result boundary must then contain no raw value. This is not forensic deletion from H2 pages, indexes, free space, database files, snapshots, or backups.

The retained tombstone has no raw value: it keeps target identity, provider/mode, digest, key ID, invalidity/audit times, accepted revision, and operation hash. A tombstone digest match is only an unprovable candidate after erasure: return stable `target-refresh-required`, leave it invalid, and create no subscription, intent, or sendable work. An active digest collision fails closed after constant-time raw-value comparison. Key loss/mismatch, failed verifier, target-mode mismatch, and tombstone candidate collision all fail closed; recovery needs the original key or an approved disposable-store reset.

## Configuration and safe failures

Shared listener inputs are `VLRGG_SERVER_HOST` (default `0.0.0.0`, ASCII `^[A-Za-z0-9.:-]{1,253}$`) and `VLRGG_SERVER_PORT` (default 8080, unsigned ASCII decimal 1–65535). Notification defaults/bounds are: 8 KiB request body (1–64 KiB), 4 KiB registration value maximum (configurable 256 B–16 KiB), active subscriptions 100 (1–1,000), poll delay 600,000 ms (60,000–86,400,000), `FID` target mode, Firebase project ID required when enabled (`^[a-z][a-z0-9-]{4,28}[a-z0-9]$`, 6–30), and app instance ID `main` (`^[a-z](?:[a-z0-9-]{0,30}[a-z0-9])?$`, 1–32). A named app is derived, never caller-supplied: `vlrgg-mn-s1-` plus 24 lowercase SHA-256 hex characters of NUL-separated `firebase-app-name-v1`, project ID, and app-instance ID. It is never Firebase's default app. Inline credential JSON is unsupported.

Booleans accept only lowercase ASCII `true`/`false`; integers are unsigned ASCII decimal with no sign, whitespace, leading coercion, or overflow. Pure validation has one deterministic `NotificationConfigurationException(category, field)` primary pair, with no raw input in messages, logs, metrics, or traces. Categories are `MISSING_REQUIRED`, `INVALID_BOOLEAN`, `INVALID_INTEGER`, `OUT_OF_RANGE`, `INVALID_SYNTAX`, `INVALID_CROSS_FIELD`, `UNSAFE_LISTENER`, `UNSAFE_STORAGE`, `UNSUPPORTED_OWNERSHIP`, `UNSUPPORTED_TARGET_MODE`, `TARGET_MODE_MISMATCH`, `FIREBASE_APP_NAME_COLLISION`, `INLINE_CREDENTIAL_UNSUPPORTED`, and `DIGEST_KEY_MISMATCH`. Fields are internal enum values for listener, feature/API, exposure/ownership/storage, each limit, Firebase project/app/mode, lookup key, and credential source. Validation order is deterministic: missing/parse/syntax/enum, then ranges, then cross-fields, listener semantics, storage/ownership, then derived app name; dependent failures with invalid prerequisites are omitted.

Pure validation and best-effort non-owning named-app precheck occur before resources. Store mode/key metadata checks may open/migrate the datasource but must finish before ADC. Acquisition failures are not configuration failures: record exactly one safe startup stage (`datasource_create`, `migration`, `store_metadata`, `adc`, `firebase_app_create`, `provider_create`, `route_install`, `tracking_job_start`, `delivery_job_start`, or `listener_bind`) plus cleanup events.

## Lifecycle, ownership, and redaction

Startup order is: (1) build the shared listener configuration, fully validate, derive/precheck app name; (2) create pool, migrate, and verify store metadata; (3) resolve ADC and atomically create the named FirebaseApp; (4) create provider; (5) install enabled routes; (6) launch supervised tracking then delivery jobs; (7) bind the constructed Netty listener. Atomic FirebaseApp creation is the ownership point. A create race closes the datasource but neither deletes the other owner's app nor uses a suffix/default-app fallback. Disabled mode invokes database, migration, ADC, FirebaseApp, provider, and job factories zero times.

Rollback and normal shutdown are LIFO: cancel/join started jobs, delete the owned named FirebaseApp once, then close the owned pool once. Cleanup continues after a cleanup failure using safe categories. `stop()` is thread-safe and idempotent; all callers share completion and resources never double-close. Listener-bind failure after module acquisition follows the same rollback.

Logs, metric labels, trace attributes, error messages, fixtures, URLs, and responses must exclude registration values (and substrings), lookup digests/key/metadata, intent IDs, request bodies, credentials/ADC source/path, Firebase project/app details, raw SDK exception or response body, provider message ID, and raw upstream material. Allowed observability is bounded categories/counters only: cycle/result/event type, lifecycle/startup stage, configuration category/field, retry terminal, retry guard, and late-result class. Required signals include cycle, Match result, intent transition, provider result/late result, unknown count, lifecycle, configuration failure, retry terminal/guard, and startup failure.

## Acceptance evidence and implementation sequence

All Stage 1 automated tests use injected Match, database, provider/SDK transport, credential, FirebaseApp, job, wall-clock, monotonic-clock, and jitter seams; offline E2E asserts zero network calls and zero real ADC resolutions. The implementation must prove: provider-neutral DTOs; separate default-disabled feature/API gates; exact shared listener preflight; strict input/revision/target isolation; observation truth table and unique intents; pre-marker reclaim/post-marker UNKNOWN/late-CAS behavior; exact retry, provider floors, jitter, and restart guard limitation; HMAC/key/tombstone logical erasure boundary; deterministic configuration and startup ledger; lifecycle LIFO; and H2 public/multi fail-fast. Tests inspect logical tables/projections/serialization, not physical H2 media, and include separate-JVM marker recovery plus route/OpenAPI, provider-adapter, lifecycle, and three offline E2E flows.

Implement after revalidating Firebase Admin, Exposed, Flyway, H2, and Java 21 primary documentation in this order: (1) configuration, listener seam, schema/repository and revision/tombstone tests; (2) local/private routes and OpenAPI; (3) tracking and unique intent creation; (4) delivery markers, adapter, retry and process tests; (5) lifecycle rollback and offline E2E; (6) full server regression, redaction/diff checks, and document reconciliation. Run targeted suites first, then `./gradlew :server:compileKotlin`, `./gradlew :server:test --rerun-tasks`, and `git diff --check`.

## Stage 2 and Stage 3 exit gates

Stage 2 is a separately approved credential/project smoke: revalidate the chosen Firebase SDK, obtain an App-supplied disposable registration value, prove it works in the selected internal target mode, then run the approved live credential/project smoke (including Firebase dry-run only here). No credential, path, registration value, or raw provider response enters repository artifacts.

Stage 3 cannot start public/production or a second process until PostgreSQL schema and migrations; H2 transfer or disposable-reset rehearsal; PostgreSQL claim/lease and isolation tests; production pooling/health/shutdown; multi-instance worker ownership; API authority distinct from target address; rate limiting/trusted proxy rules; encryption/KMS/key rotation; low-cardinality dashboards/alerts; and backup, restore, UNKNOWN-adjudication, and recovery runbooks are approved and verified. Configuration must fail fast for `PUBLIC`/`PRODUCTION` with H2 or `SINGLE_PROCESS`, and for multi-instance ownership with H2.
